# Implementation notes

## Data flow

1. An administrator creates a company with an uploaded logo, contact data, address, chatbot alias, greeting template, and one of four distinct avatar choices: Bot, Brain Circuit, Headset, or Book Check. PostgreSQL stores the unchanged greeting template rather than rendered values. Templates are limited to 400 characters and may use only `{{bot_alias}}` and `{{company_name}}`; unknown or malformed placeholders are rejected. The Chatbot UI replaces every occurrence with the active company's current values at the beginning of each new chat session, so later company-name or bot-alias changes are reflected automatically.
2. PostgreSQL stores the company profile plus the logo as binary data with its MIME type. Logos are limited to 512 KB and PNG, SVG, or JPEG; SVG uploads are parsed and rejected when they contain active content. The company service embeds Company Name, About, Contact Details, and Address as separate, labeled Qdrant chunks when those values are present. Logo bytes are served through dedicated endpoints and are never included in company JSON or vector chunks.
3. The administrator chooses either a PDF or one public web-page URL. PDF preview uploads bytes with `company_id`; URL preview sends JSON containing `company_id` and the URL.
4. For PDFs, the Admin API validates MIME type, signature, size, encryption state, and page count before returning page excerpts. For URLs, it validates every initial/redirect hostname against public IP ranges, enforces redirect, timeout, response-size, status, and HTML content-type limits, strips boilerplate, and returns extracted text with detected headings preserved.
5. The user names the knowledge base and configures a chunking strategy. PDF imports additionally support included/excluded page selection; URL imports represent one page with no page-number metadata in Qdrant.
6. The import service creates ID-scoped chunks, gets embeddings from Ollama, and stores dense plus lexical vectors in Qdrant. PDFs support all four strategies. URLs support only the structure-aware Recursive and Hierarchical strategies; Recursive is the default. The Admin UI disables Fixed-size and Semantic for URL previews, and the Admin API plus import service independently reject those combinations.

The Admin API calculates a SHA-256 checksum from uploaded PDF bytes or normalized extracted web text. It checks for existing content during preview and immediately before import, while PostgreSQL's unique `(company_id, document_checksum)` index provides the final concurrency-safe guarantee. The single `source` column stores a PDF filename or final web URL, and `mime_type` distinguishes them. Filenames are not treated as identity because revised documents commonly retain their original filename. A MIME-filtered unique index on `(company_id, source)` applies only to HTML rows. When that URL already exists but its checksum has changed, the service indexes a new ID, atomically replaces the database row, then deletes the old vectors; retrieval can no longer select the old ID even if best-effort vector cleanup must be retried. The previous enabled/disabled state is preserved.

7. Knowledge-base metadata and the complete import configuration are saved to PostgreSQL with a required company relationship. Source identity uses only `source` and `mime_type`; there are no knowledge-base `source_type`, `source_url`, or `filename` columns. PDF page selection is stored compactly as `excluded_pages_json` plus an integer `selected_pages` count; the full selected-page list is not duplicated. URL imports store `total_pages`, `selected_pages`, and `excluded_pages_json` as SQL `NULL`.
8. Admin UI's **Try ChatBot** action creates the session through the Chat API before navigation. The backend generates the session ID, stores an `active` row and rendered company greeting, and returns session/company/transcript context plus an authoritative `expires_at`. Chatbot UI opens with only `?session_id=...`, reloads its transcript from PostgreSQL, and derives the countdown from that backend expiry rather than browser timestamps.
9. Starting a new conversation sends the current ID as `previous_session_id`; the backend closes it before creating the replacement and the UI replaces its URL with the new session ID. The top-right close action stores `closed`, and a `pagehide` beacon calls the idempotent unload-close endpoint when the browser tab is destroyed; hard and inactivity expiry store `timeout`. The repository sets `ended_at` only on the first active-to-ended transition, making repeated close requests safe. On every session-context, source, chat, stream, and escalation request, the backend computes hard expiry from database `created_at` plus `CHAT_SESSION_MINUTES`, transitions expired active sessions to `timeout`, and rejects non-active sessions. A backend sweep also performs this transition every `CHAT_SESSION_SWEEP_SECONDS`, covering sessions where an unload beacon cannot be delivered.
10. Chat and source APIs require only the session ID. The backend resolves the company from the session row, selects only that company's enabled sources, persists the user message, embeds the question, and runs reciprocal-rank fusion over dense semantic and sparse lexical candidates. This prevents callers from changing company scope within an established session. Company-profile chunks are always eligible for that company, including when no PDF knowledge base is selected. The selected passages, limited conversation history, and grounding rules are sent to the OpenAI, Anthropic, Hugging Face, or Ollama client selected by that company's `company_llm_mappings` row. A completed bot answer is persisted with the provider-reported input/output token usage, and citations are returned separately so the UI can show their actual page or company-profile label.

## Chat-session persistence and review

`chat_sessions` stores the session ID, company foreign key, `active`/`closed`/`timeout` status, client IP address, creation time, and optional end time. `chat_session_messages` stores an ordered UUID message ID, session foreign key, `bot`/`user` owner, text content, separate non-negative `input_tokens` and `output_tokens`, and creation time. Token usage is attached only to generated bot responses using OpenAI Responses usage, Anthropic Messages usage, Hugging Face OpenAI-compatible usage, or Ollama evaluation counts. Greetings and user messages remain zero. Startup migration adds both token columns with zero defaults for existing rows. Both foreign keys use cascading deletion, and the repository explicitly clears session rows during company deletion for SQLite-compatible behavior. Composite indexes support company/date browsing and ordered transcript reads.

The Admin API exposes a company-scoped, server-paginated session list with a required inclusive date range capped at 14 calendar days, plus a session-detail endpoint with messages sorted oldest-first. Its bulk-delete endpoint accepts either up to 100 session IDs or an inclusive company/date filter with the same 14-day cap. It deletes only company-owned rows and explicitly removes transcript rows for SQLite-compatible behavior. Admin UI's **Chat Sessions** item reuses the active-company selector, constrains its date controls to the same 14-day maximum, offers an immediate refresh action, lists sessions newest-first, supports page-level multi-selection and confirmed deletion, and provides a separate filter-row action that deletes all matching sessions across pagination. It renders a selected transcript in a read-only conversation view with no composer, source selector, countdown, keep-session prompt, or lifecycle controls.

The Admin API also aggregates company analytics by the session creation date for an inclusive range capped at 90 days. Its response includes total sessions, messages, average messages per session, input/output token totals, and a zero-filled daily series. The Admin UI **Analytics** dashboard renders four summary cards plus separate daily session, message, and token trend charts. The token chart plots total, input, and output series, while each chart keeps its requested totals or averages in a right-side legend.

Knowledge bases can be disabled without deleting their data. Disabled sources are excluded both from the Chat API source list and from server-side retrieval, even if a client submits their IDs directly. Qdrant retrieval and hard deletion filter directly on `company_id` and `knowledge_base_id`; PostgreSQL resolves the knowledge-base display name only after retrieval for citations. If Qdrant deletion fails, the PostgreSQL metadata is retained and the API returns an error so orphaned chunks are not silently created.

Company names preserve their submitted letter casing after trimming and collapsing whitespace. Case-insensitive API checks and a unique index on `lower(company.name)` prevent case-only duplicates. Knowledge-base names are trimmed, whitespace-normalized, and converted to uppercase. The Admin API returns `409 Conflict` for duplicates. Composite unique indexes on `(company_id, name)` and `(company_id, document_checksum)` provide concurrency-safe knowledge-base enforcement. Startup migration creates a default company for legacy knowledge bases and replaces superseded indexes.

A company has zero or one `company_llm_mappings` row with columns ordered as `id`, `company_id`, `provider`, `model`, `api_key_encrypted`, `created_at`, and `updated_at`; `company_id` is unique and references the company. New companies remain unconfigured until an administrator explicitly selects a provider and model. Remote-provider credentials are encrypted per company with the deployment's `LLM_CREDENTIALS_KEY`. They are accepted as write-only input and decrypted only to create a provider client or derive the fixed-length Admin UI preview containing their first and last two characters. The complete key and ciphertext are never returned. Selecting Ollama nulls `api_key_encrypted`. Available models are supplied per provider through `OPENAI_MODELS`, `ANTHROPIC_MODELS`, `HUGGINGFACE_MODELS`, and `OLLAMA_MODELS`. The mutable `companies` and `knowledge_bases` tables also maintain `updated_at`. Retrieval embeddings use the platform-level `EMBEDDING_MODEL`, independently of the company's answer provider, so switching answer providers does not require re-indexing knowledge.

For databases created by an earlier version, startup migration adds the binary logo and MIME-type columns and drops the obsolete `logo_url` column. It also renames knowledge-base `filename` to `source`, copies existing web URLs into that field, removes the obsolete knowledge-base `source_type` and `source_url` columns, and replaces their index with the HTML-only source index. Existing external company-logo URL values are not downloaded automatically; administrators can upload the corresponding logo from the company editor.

Deleting a company first removes every Qdrant point carrying its `company_id`, then deletes the company and all related knowledge-base rows from PostgreSQL. If Qdrant is unavailable, PostgreSQL records are retained and the API returns `503`, allowing the operation to be retried without leaving vector data orphaned. Company renames do not require document-vector updates because the stable company ID is used for correlation.

Company creates and updates are consistency-sensitive writes rather than best-effort fallback writes. Embeddings are prepared first, old `company_metadata` points are deleted by company ID, and the complete current profile is synchronously persisted to Qdrant before PostgreSQL is updated. A vector failure returns `503`, keeps the PostgreSQL record unchanged, and cleans process-local partial metadata so the request can be safely retried.

## Chunk metadata

Every Qdrant payload has the compact top-level shape `company_id`, `knowledge_base_id`, `text`, `source_type`, and `metadata`. This vector-only `source_type` distinguishes ordinary knowledge chunks from `company_metadata`; it is unrelated to the removed knowledge-base database column. Company and knowledge-base names and web URLs are not stored in Qdrant; PostgreSQL resolves them after retrieval. PDF chunk metadata contains `page_number` and `section` (nullable when no heading is detected). URL chunks omit `page_number` and retain their detected section. Fixed, recursive, and semantic chunks are flat and therefore do not store a breadcrumb. Hierarchical chunks add `level` and a semantic breadcrumb containing only detected section/title ancestry, for example `["Employee Handbook", "Leave Policy", "Exceptions"]`. Page location remains solely in `page_number`, and parent-child linkage remains solely in `parent_id`. Chunk index and strategy are not duplicated in vector metadata because the import configuration remains in PostgreSQL. Company-profile points use `source_type=company_metadata` and contain only their section label under `metadata`; they do not store page number, breadcrumb, or parent ID.

Chunk size and overlap are character targets rather than permission to split prose. Fixed, recursive, semantic, and hierarchical chunking align their windows to complete sentence boundaries; semantic chunks prefer complete paragraph units. Overlap reuses complete trailing sentences or paragraphs, walking backward only to the nearest available unit boundary. Consequently, a chunk or its effective overlap may exceed the configured target when that is required to preserve sentence integrity. A sentence longer than the configured chunk size remains intact, and the chunker advances without repeating that entire chunk.

This payload layout is a clean schema cutover. Existing name-based Qdrant points are not migrated automatically; clear and reindex existing data before using this version.

## Resilience and boundaries

- Ollama embedding failure falls back to deterministic feature-hashed vectors for development.
- Chat retrieval and ordinary development writes can fall back to an in-process index. Company-profile creates and updates deliberately require Qdrant persistence and return `503` on failure because silent fallback could leave stale durable metadata. The process-local fallback remains non-durable and cannot cross API processes.
- Model prompts explicitly require answers from retrieved context and a clear admission when context is insufficient.
- The 40 MB upload limit and PDF signature check happen before parsing.
- URL fetching accepts only public HTTP/HTTPS HTML, revalidates every redirect target, rejects credentials and non-public resolved addresses, and streams at most `WEB_FETCH_MAX_BYTES` within `WEB_FETCH_TIMEOUT`. It deliberately does not execute client-side JavaScript or crawl linked pages.
- User conversation history is cached in browser storage for continuity and durably persisted in PostgreSQL; only the latest 12 turns are sent to the model.
- The stop button aborts the browser request. Human escalation creates a reference record behind a replaceable endpoint; integrate that endpoint with a ticketing provider for production.

## Extension points

- Implement `VectorStore` to use a different vector database.
- Implement `KnowledgeRepository` to use an existing metadata service or add authorization rules around company scope.
- Add another answer provider by implementing the small chat/stream client protocol and extending the provider factory and allowlist; retrieval and import services remain unchanged.
- Add OCR in `DocumentStore.extract` for scanned PDFs.
- Extend `WebDocumentFetcher` with an explicitly bounded same-origin crawler if multi-page website ingestion is required.
- Add authentication/authorization middleware before public deployment. Company scope is enforced by data queries, but caller identity still needs to be mapped to authorized companies.

## Production checklist

- Add an identity provider and tenant-aware authorization.
- Replace automatic schema creation with Alembic migrations.
- Persist upload ownership and asynchronous ingestion jobs.
- Connect escalation to the organization’s support queue.
- Configure PostgreSQL/Qdrant backups, TLS, secret management, rate limits, audit logs, and observability.
- Pin approved frontend dependency versions through the generated lockfile and use an internal package registry if required.
